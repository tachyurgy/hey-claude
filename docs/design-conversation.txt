The clean way to think about it is a two-stage pipeline: a lightweight always-on wake-word detector that does nothing but listen for "hey claude," and a trigger handler that fires once detected and launches your agent. You don't want full speech recognition running 24/7 (heavy on CPU/battery and privacy); you want a tiny model gating a bigger one.
Here's how I'd build each piece.
Wake-word detection
The easiest and most reliable option is Picovoice Porcupine. It runs fully on-device, uses almost no CPU, and lets you train a custom "hey claude" keyword in their web console (free personal tier). You download a .ppn keyword file and feed it mic frames.
pythonimport pvporcupine
from pvrecorder import PvRecorder
import subprocess

porcupine = pvporcupine.create(
    access_key="YOUR_PICOVOICE_KEY",
    keyword_paths=["hey-claude_en_mac_v3.ppn"],  # your trained file
    sensitivities=[0.6],  # higher = more sensitive, more false positives
)

recorder = PvRecorder(frame_length=porcupine.frame_length)
recorder.start()
print("Listening for 'hey claude'...")

try:
    while True:
        pcm = recorder.read()
        if porcupine.process(pcm) >= 0:
            print("Wake word detected!")
            launch_agent()
except KeyboardInterrupt:
    pass
finally:
    recorder.delete()
    porcupine.delete()
Install with pip install pvporcupine pvrecorder.
Alternatives if you want to avoid an account: openWakeWord is fully open-source and local, but custom phrases need you to train a small model (it ships with a synthetic-data pipeline). And the brute-force route is running whisper.cpp or faster-whisper continuously with voice-activity-detection gating, then string-matching "hey claude" in the transcript — flexible and no custom training, but much heavier. I'd start with Porcupine and only move to the others if licensing or cost matters.

Keeping it always running + the macOS gotchas
To make it persistent, wrap the listener script in a launchd agent. Create ~/Library/LaunchAgents/com.you.heyclaude.plist:
xml<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">

</plist>
Load it with launchctl load ~/Library/LaunchAgents/com.you.heyclaude.plist. KeepAlive restarts it if it crashes; RunAtLoad starts it at login.
Two things that will trip you up:
The big one is microphone permissions. macOS requires explicit mic access (System Settings → Privacy & Security → Microphone). A Python process launched by launchd often can't trigger the permission prompt and will silently get empty audio. The reliable fix is to bundle the script as a small .app (via something like py2app or even an Automator/Shortcuts wrapper) so it has a stable identity macOS can grant permission to — or during development, run it once from Terminal and grant Terminal mic access so the prompt appears.
The second is that launchd agents run in a limited environment — no PATH, no shell profile. Use absolute paths for both python3 and claude (find the latter with which claude), and pass your ANTHROPIC_API_KEY via an EnvironmentVariables dict in the plist if the agent needs it.

Knowing when to stop: endpointing
What you want is called endpointing or voice activity detection (VAD). The naive version is energy-based: record frames, measure volume, and stop once you've seen ~800ms of audio below a threshold. That works but it's flaky — it'll cut you off mid-pause or keep going forever in a noisy room.
The robust version is Silero VAD, a tiny neural model that classifies each chunk as speech/not-speech far more reliably than raw volume. The pattern is: keep a rolling counter of consecutive silent frames, and once it crosses your "hang time" (typically 700–1000ms), stop.
pythonimport numpy as np
import sounddevice as sd
import torch

vad_model, _ = torch.hub.load('snakers4/silero-vad', 'silero_vad')

def record_until_silence(samplerate=16000, hang_ms=800, max_seconds=15):
    frames = []
    silent_chunks = 0
    chunk = int(0.032 * samplerate)          # 32ms windows
    hang_chunks = int(hang_ms / 32)
    started = False

    with sd.InputStream(samplerate=samplerate, channels=1, dtype='float32') as stream:
        for _ in range(int(max_seconds * samplerate / chunk)):
            audio, _ = stream.read(chunk)
            audio = audio.flatten()
            frames.append(audio)
            prob = vad_model(torch.from_numpy(audio), samplerate).item()

            if prob > 0.5:
                started = True
                silent_chunks = 0
            elif started:
                silent_chunks += 1
                if silent_chunks > hang_chunks:
                    break                     # they stopped talking

    return np.concatenate(frames)
Two refinements worth adding: a max duration cap (above) so a stuck detector doesn't record forever, and a small pre-roll buffer — keep the ~300ms of audio from before speech started, since people often begin talking the instant the wake word fires and you'll clip the first syllable otherwise.
Transcription: you mean MLX (or Metal), not GLX
GLX is a Linux/X11 OpenGL thing — it doesn't exist on Mac. On Apple Silicon you've got two good GPU-accelerated paths:
mlx-whisper — built on Apple's MLX framework (almost certainly what you meant). It's the fastest option on M-series chips and dead simple:
pythonimport mlx_whisper

def transcribe(audio):
    result = mlx_whisper.transcribe(
        audio,
        path_or_hf_repo="mlx-community/whisper-large-v3-turbo"
    )
    return result["text"].strip()
Install with pip install mlx-whisper. The turbo model is the sweet spot — near-large-v3 accuracy at a fraction of the time, transcribes a short command in well under a second.
whisper.cpp — uses Metal for GPU acceleration and runs as a standalone binary, so you shell out to it instead of importing. Good if you'd rather not have Python ML deps, but for your use case mlx-whisper is less fiddly.
(Note: faster-whisper, which I'd otherwise recommend, runs CPU-only on Mac — it doesn't use the GPU. Skip it here.)
Passing to Claude Code — the flag is -p, not -b
Small correction: the headless flag is -p (short for --print). There's a separate --bare flag — possibly what your "-b" was reaching for — but they do different jobs and you'll likely want both.
-p is what makes it non-interactive: it processes the prompt, outputs the result to stdout, and exits — no waiting for user input. The AI Agent Factory
--bare is a newer speed/reproducibility flag: it reduces startup time by skipping auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md. The catch is auth — bare mode skips OAuth and keychain reads, so authentication must come from ANTHROPIC_API_KEY or an apiKeyHelper. So if you use --bare you must have ANTHROPIC_API_KEY set; if you'd rather use your subscription login, drop --bare and just use -p. ClaudeClaude
Wiring the whole thing together, your launch_agent() becomes:
pythonimport subprocess

def launch_agent():
    audio = record_until_silence()
    command = transcribe(audio)
    if not command:
        return

    subprocess.Popen([
        "claude", "-p", command,
        "--output-format", "json",
        "--allowedTools", "Read,Edit,Bash",
        # add "--bare" only if ANTHROPIC_API_KEY is set
    ])
One thing worth deciding early: in headless mode there's no human to approve tool calls, so you have to pre-authorize. Be careful scoping --allowedTools — the safe pattern is narrow grants like "Bash(git:*)" rather than blanket Bash, since a wide-open headless agent triggered by your voice (with all the false-positive risk that carries) can do real damage before you notice. I'd also consider adding --max-turns as a circuit breaker so a misfire can't run away.
So the full chain is: Porcupine detects "hey claude" → Silero VAD records until you stop talking → mlx-whisper transcribes → claude -p runs the agent. Let me correct the launch step.
claude -p is a one-shot call — it runs in the foreground, prints to stdout, and exits, so it's not really "an agent running in the background," it's a blocking subprocess. What you want is Agent View: one command, claude agents, gives you a dashboard of every Claude Code session running on your machine, where each row is a full conversation that keeps running with no terminal attached. The key property for your use case is persistence — the work is hosted by a per-user supervisor process that sits separately from your terminal, so background sessions are detached child processes the supervisor manages. Sessions survive terminal closure, so you can shut your laptop and the agents keep coding. Substack + 2
So the flow becomes: each "hey claude" dispatches a new detached session into the supervisor, and you watch/attach via claude agents whenever you want. To dispatch one non-interactively from your script, the alias is claude --bg — Agent View sessions can be launched with claude agents or claude --bg, as local persistent sessions managed by a supervisor independent of your terminal. That changes launch_agent() to fire-and-forget a background session instead of blocking on a one-shot:
pythonimport subprocess

def launch_agent():
    audio = record_until_silence()
    command = transcribe(audio)
    if not command:
        return

    # Dispatch a detached background session into the supervisor.
    # Returns immediately; the agent keeps running independent of this process.
    subprocess.Popen(
        ["claude", "--bg", command, "--permission-mode", "acceptEdits"],
        stdout=subprocess.DEVNULL,
        stderr=subprocess.DEVNULL,
    )
A few things this design gets you that the -p version didn't. Your wake-word listener stays free immediately after dispatching, so you can say "hey claude" again and queue up a second agent while the first is still working — they all show up as separate rows in claude agents. And because the supervisor owns them, a misfire or a long-running task doesn't tie up your listener process.
Two practical notes. The dispatch flags landed recently — claude agents gained --add-dir, --settings, --mcp-config, --permission-mode, --model, --effort, and --dangerously-skip-permissions for configuring dispatched background sessions — so make sure your Claude Code is current, and use --permission-mode (or scoped --allowedTools) rather than letting a voice-triggered agent hit a permission wall it can't answer. And if you want your listener to know what's running — say, to avoid spawning ten duplicates from ten false wake-word fires — claude agents --json lists live Claude sessions as JSON for scripting, so you can poll it and gate on the current session count.
