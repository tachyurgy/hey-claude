Architected wake-word detection pipeline with agent launch strategy

Good project — this is very doable on macOS. The clean way to think about it is a two-stage pipeline: a lightweight always-on wake-word detector that does nothing but listen for "hey claude," and a trigger handler that fires once detected and launches your agent. You don't want full speech recognition running 24/7 (heavy on CPU/battery and privacy); you want a tiny model gating a bigger one.

Here's how I'd build each piece.
Wake-word detection

The easiest and most reliable option is Picovoice Porcupine. It runs fully on-device, uses almost no CPU, and lets you train a custom "hey claude" keyword in their web console (free personal tier). You download a .ppn keyword file and feed it mic frames.
python

import pvporcupine
from pvrecorder import PvRecorder
import subprocess

porcupine = pvporcupine.create(
    access_key="YOUR_PICOVOICE_KEY",
    keyword_paths=["hey-claude_en_mac_v3.ppn"],  # your trained file
    sensitivities=[0.6],  # higher = more sensitive, more false positives
)

recorder = PvRecorder(frame_length=porcupine.frame_length)
recorder.start()
print("Listening for 'hey claude'...")

try:
    while True:
        pcm = recorder.read()
        if porcupine.process(pcm) >= 0:
            print("Wake word detected!")
            launch_agent()
except KeyboardInterrupt:
    pass
finally:
    recorder.delete()
    porcupine.delete()

Install with pip install pvporcupine pvrecorder.

Alternatives if you want to avoid an account: openWakeWord is fully open-source and local, but custom phrases need you to train a small model (it ships with a synthetic-data pipeline). And the brute-force route is running whisper.cpp or faster-whisper continuously with voice-activity-detection gating, then string-matching "hey claude" in the transcript — flexible and no custom training, but much heavier. I'd start with Porcupine and only move to the others if licensing or cost matters.

Two things that will trip you up:

The big one is microphone permissions. macOS requires explicit mic access (System Settings → Privacy & Security → Microphone). A Python process launched by launchd often can't trigger the permission prompt and will silently get empty audio. The reliable fix is to bundle the script as a small .app (via something like py2app or even an Automator/Shortcuts wrapper) so it has a stable identity macOS can grant permission to — or during development, run it once from Terminal and grant Terminal mic access so the prompt appears.

The second is that launchd agents run in a limited environment — no PATH, no shell profile. Use absolute paths for both python3 and claude (find the latter with which claude), and pass your ANTHROPIC_API_KEY via an EnvironmentVariables dict in the plist if the agent needs it.

Yes, silence is exactly it — though "stop after silence" is slightly trickier than it sounds, and you've got two small naming mix-ups (GLX, -b) that I'll sort out as we go.
Knowing when to stop: endpointing

What you want is called endpointing or voice activity detection (VAD). The naive version is energy-based: record frames, measure volume, and stop once you've seen ~800ms of audio below a threshold. That works but it's flaky — it'll cut you off mid-pause or keep going forever in a noisy room.

The robust version is Silero VAD, a tiny neural model that classifies each chunk as speech/not-speech far more reliably than raw volume. The pattern is: keep a rolling counter of consecutive silent frames, and once it crosses your "hang time" (typically 700–1000ms), stop.
python

import numpy as np
import sounddevice as sd
import torch

vad_model, _ = torch.hub.load('snakers4/silero-vad', 'silero_vad')

def record_until_silence(samplerate=16000, hang_ms=800, max_seconds=15):
    frames = []
    silent_chunks = 0
    chunk = int(0.032 * samplerate)          # 32ms windows
    hang_chunks = int(hang_ms / 32)
    started = False

    with sd.InputStream(samplerate=samplerate, channels=1, dtype='float32') as stream:
        for _ in range(int(max_seconds * samplerate / chunk)):
            audio, _ = stream.read(chunk)
            audio = audio.flatten()
            frames.append(audio)
            prob = vad_model(torch.from_numpy(audio), samplerate).item()

            if prob > 0.5:
                started = True
                silent_chunks = 0
            elif started:
                silent_chunks += 1
                if silent_chunks > hang_chunks:
                    break                     # they stopped talking

    return np.concatenate(frames)

Two refinements worth adding: a max duration cap (above) so a stuck detector doesn't record forever, and a small pre-roll buffer — keep the ~300ms of audio from before speech started, since people often begin talking the instant the wake word fires and you'll clip the first syllable otherwise.

Reconciled background agent dispatch mechanism with user correction

You're right, and that's a meaningfully different (better) design than what I sketched. Let me correct the launch step.

claude -p is a one-shot call — it runs in the foreground, prints to stdout, and exits, so it's not really "an agent running in the background," it's a blocking subprocess. What you want is Agent View: one command, claude agents, gives you a dashboard of every Claude Code session running on your machine, where each row is a full conversation that keeps running with no terminal attached. The key property for your use case is persistence — the work is hosted by a per-user supervisor process that sits separately from your terminal, so background sessions are detached child processes the supervisor manages. Sessions survive terminal closure, so you can shut your laptop and the agents keep coding.
Substack + 2

So the flow becomes: each "hey claude" dispatches a new detached session into the supervisor, and you watch/attach via claude agents whenever you want. To dispatch one non-interactively from your script, the alias is claude --bg — Agent View sessions can be launched with claude agents or claude --bg, as local persistent sessions managed by a supervisor independent of your terminal.
Wmedia

That changes launch_agent() to fire-and-forget a background session instead of blocking on a one-shot:
python

import subprocess

def launch_agent():
    audio = record_until_silence()
    command = transcribe(audio)
    if not command:
        return

    # Dispatch a detached background session into the supervisor.
    # Returns immediately; the agent keeps running independent of this process.
    subprocess.Popen(
        ["claude", "--bg", command, "--permission-mode", "acceptEdits"],
        stdout=subprocess.DEVNULL,
        stderr=subprocess.DEVNULL,
    )

A few things this design gets you that the -p version didn't. Your wake-word listener stays free immediately after dispatching, so you can say "hey claude" again and queue up a second agent while the first is still working — they all show up as separate rows in claude agents. And because the supervisor owns them, a misfire or a long-running task doesn't tie up your listener process.

Two practical notes. The dispatch flags landed recently — claude agents gained --add-dir, --settings, --mcp-config, --permission-mode, --model, --effort, and --dangerously-skip-permissions for configuring dispatched background sessions — so make sure your Claude Code is current, and use --permission-mode (or scoped --allowedTools) rather than letting a voice-triggered agent hit a permission wall it can't answer. And if you want your listener to know what's running — say, to avoid spawning ten duplicates from ten false wake-word fires — claude agents --json lists live Claude sessions as JSON for scripting, so you can poll it and gate on the current session count.

No — Porcupine doesn't record or train on their voice

This is the part to get straight. Porcupine doesn't enroll a person's voice. You train and test a custom wake word by typing it — you go to the Picovoice Console, type "hey claude" as text, and it generates the .ppn model from that. Training takes seconds with no training dataset or machine learning expertise required. No recording step.
Picovoice
Picovoice

And critically, the result is speaker-independent: the model responds to anyone saying "hey claude," not just the person who set it up. That's usually what you want for a published tool — every user shouldn't have to retrain it.

If you actually wanted the voice itself to be the trigger — i.e. only your voice wakes it, rejecting everyone else — that's a different technology called speaker recognition, and Picovoice does it with a separate engine, Eagle. The documented pattern is two-stage: detect a custom wake word with Porcupine, then verify the speaker with Eagle, so it responds only to enrolled users on shared devices. Eagle is the one that records and enrolls a voice. So: Porcupine = "is someone saying the phrase" (text-trained), Eagle = "is it this person" (voice-enrolled). Most "hey claude" setups only need the first.

The licensing catch that affects publishing

Before you build a distributable package around Porcupine, know this: Picovoice Personal accounts can train custom models only subject to limitations and strictly for non-commercial purposes; commercial settings and distribution require an Enterprise account. Publishing a Homebrew package others install leans toward "distribution." Also, the AccessKey is per-user and must stay secret — anyone using Picovoice needs their own valid AccessKey for authentication — so you literally cannot bundle yours; every user signs up and supplies their own.

Homebrew: it can do the plumbing, not the permissions

Yes for the mechanical dependencies, no for the three things that actually gate a working install.

Homebrew handles system/binary deps cleanly via depends_on — portaudio (mic capture), python@3.12, ffmpeg, node (for Claude Code), etc. Python package deps are doable too: the standard formula pattern vendors each PyPI dependency as a resource block installed into a virtualenv (brew update-python-resources helps generate them). The honest caveat is that the ML deps here are heavy — pulling in PyTorch (for Silero VAD) and mlx-whisper through Homebrew resources is genuinely painful. A common shortcut is to keep Homebrew for the system libs and let the formula create a venv and pip install the Python stack at install time, or just ship the whole thing on PyPI and have people pipx install it, using brew only for portaudio/ffmpeg.

What no package manager can automate, and what will actually trip up your users:

The microphone permission. macOS TCC requires explicit user approval, and a brew-installed bare CLI inherits the terminal's mic permission — fragile and confusing. This is the same reason I flagged earlier that bundling as a small .app is cleaner: an app has a stable identity macOS can grant mic access to, and the permission prompt actually fires. If you go that route you'd distribute a Homebrew cask (for the .app) rather than a formula.

The secrets and auth. The Picovoice AccessKey, the ANTHROPIC_API_KEY (or Claude Code login), and Claude Code itself all have to come from the user. Best you can do is a caveats block in the formula that prints setup instructions on install, plus a guided first-run that checks for each and walks them through it.

So the realistic shape: a tap (brew tap you/heyclaude && brew install heyclaude) — or a cask if you wrap it as an app — that installs the binaries and Python env automatically, then a first-run wizard that handles mic permission, keys, and a quick check that claude is on PATH. The install gets you 80% there; that wizard is the other 20% no formula can cover.

Synthesized three-stage architecture and practical training tradeoffs

openWakeWord's whole design is one clever bet: don't train a wake-word model from scratch, just train a tiny classifier on top of a powerful pre-trained speech model that someone else already built. That's what lets it work without you recording any audio.

It's a three-stage pipeline that runs on each chunk of mic audio:

First, a melspectrogram model converts raw audio into frequency features — it takes a chunk of about 1280 samples at 16kHz (~80ms) and turns it into a mel spectrogram. This is just standard audio preprocessing.
Outspoken

Second, and this is the important part, a frozen embedding model turns those spectrograms into compact audio embeddings. This is Google's pre-trained speech_embedding model producing 96-dimensional embeddings; the backbone is frozen and shared, so every wake word model you load runs through the same embedding pass once per frame. This shared feature extractor is the core component — it gains its strong performance from extensive pre-training on large amounts of data, and it's what enables good accuracy even when training only on synthetic data. Think of it as a model that already "understands speech" in general; you never touch or retrain it.
Codeline
GitHub

Third, a lightweight classification head — your actual "hey claude" model — runs on top of those embeddings and answers one question: is this the wake word? These heads are small fully-connected networks or 2-layer RNNs, fast, and trained only on synthetic speech. One nice detail for catching a multi-word phrase: the classifier doesn't look at just one chunk — it maintains a sliding window of the last 16 embeddings (~1.3 seconds) and scores the whole window each step, which is what lets it detect a phrase spanning multiple chunks.
Codeline
Outspoken
How a custom model gets trained

Here's where it answers your earlier voice question directly: like Porcupine, it does not record or enroll your voice, and it's speaker-independent. The training data is entirely fake. Piper TTS generates thousands of synthetic pronunciations of your wake word with varying voices, speeds, and pitch; each clip is then layered with room reverb, background noise, and varied acoustic conditions; and finally a small neural network learns to distinguish your wake word from everything else. The included pre-trained models were all trained with 100% synthetic speech generated from text-to-speech models, requiring little to no manual data collection. The output is tiny — an ONNX (and TFLite) model under 250KB.

The real tradeoff vs Porcupine

The catch is that training is more involved than Porcupine's "type the phrase in a web console and download." "hey claude" isn't one of the bundled phrases, so you'd run the training pipeline yourself — it generates clips, augments them, and trains, which takes roughly an hour on a decent GPU — or use a hosted helper (there are services and a Colab notebook that'll spit out the .onnx for you in ~45 minutes). So: Porcupine is faster to set up but has the per-user key and non-commercial limitation; openWakeWord is more upfront work to train but then ships freely with no key and no signup, which is why it fits a published package better.
